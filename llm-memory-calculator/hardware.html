How the pieces connect

Three different questions, each answered by a different knob. Mixing them up is where the confusion comes from.

1 · Instance need

Weights plus KV cache plus fixed state, from page 1. Only the model, context, users and fill change it. Divide by 0.92 to get the memory to plan for. The catalog's 32, 48, 64 and 96 GB sizes are starting points set by model size alone; this page sizes for your actual workload and shows the nearest one.

2 · NUMA node budget

Either run one copy of the model per NUMA node with the users split between them, or one tensor-parallel instance that spreads the weights and KV cache across all nodes. vLLM reserves 92% of each node's memory at startup, whatever the instance needs; the OS keeps the rest. What lands on each node must fit inside that 92%.

3 · Host DIMMs

Every memory channel gets a DIMM, because decode speed is set by memory bandwidth. The DIMM count is fixed by the processor (sockets × channels, × 2 at two per channel); the DIMM size only buys capacity. Two per channel buys more capacity but slows DDR5 to 5200. MRDIMM or DDR5-8000 raise bandwidth, which raises tokens per second.

Why bandwidth sets speed

Each new token reads the weights from memory once. So one user can't go faster than bandwidth ÷ weight size. A mixture-of-experts model reads only the experts it uses: one user reads the active parameters, a big batch reads close to all of them. Real speed lands below this ceiling, but it moves with it.

Where the numbers come from

  • Every processor figure (cores, TDP, memory types and speeds, memory channels per socket, and how many sockets it supports) comes from that SKU's specifications page on Intel ARK, checked on 28 November 2026, and was cross-checked against Supermicro's Xeon 6 SKU table. Each row in the table links to its ARK page. Only P-core server SKUs are listed, because AMX, the matrix engine vLLM uses for BF16, is on P-cores; the -B SoC parts and the Xeon 6300 entry series are left out.
  • MRDIMM speed: Intel's MRDIMM support article gives up to 8800 MT/s on Xeon 6900P and 8000 MT/s on Xeon 6500P/6700P. DDR5-8000 RDIMM: Intel is enabling it at one DIMM per channel on select Xeon 6700P SKUs through a platform and BIOS update (Intel newsroom, July 2026, measured on 2 × Xeon 6787P with 16 × 64 GB). Ask the server maker which SKUs and boards qualify. Two DIMMs per channel run DDR5 at 5200 MT/s on Xeon 6700P/6500P (Kingston, Birch Stream memory).
  • The 92% reservation per NUMA node: Intel Inference Microservices, Environment variables (gpu-memory-utilization, default 0.92). Its startup error checks the memory available on the node, so the OS, other processes and the page cache count against it. Memory sizes 32/48/64/96 GB: Supported Intel platforms, where they are starting points by model size (2–9B, 10–16B, 17–24B, 25–30B including mixture-of-experts), not workload classes.
  • Peak bandwidth per socket = channels × 8 bytes × transfer rate. It's the theoretical peak; the "bandwidth you actually get" slider scales it. For scale, heise measured 1.21 TB/s with a STREAM-triad-like pattern on 2 × Xeon 6980P with MRDIMM-8800, about 72% of the 1.69 TB/s peak (heise). Intel quotes DDR5-8000 as 25% faster per transfer but up to 20% more measured bandwidth than DDR5-6400.
  • Sub-NUMA modes follow the compute dies, since each die carries its own memory controllers: Xeon 6900P has three dies and offers SNC3 (the default) or HEX, one node per socket (Phoronix). Xeon 6700P/6500P use either two dies (such as the 86-core parts) or one (The Register), so SNC2 exists only on two-die parts. The selector offers only the modes that split the channels evenly; check your server with numactl -H.
  • DIMM sizes are binary (a "64 GB" DIMM is 64 GiB, about 68.7 GB), while the model and KV cache figures are decimal GB. The page counts DIMMs at their label, which leaves about 7% unclaimed and errs on the safe side.
  • Why bandwidth sets speed: Intel describes LLM inference on Xeon as "a memory-bound workload", with memory reads as the largest hot spot (Boost LLMs with PyTorch on Intel Xeon). The ceiling on this page (bandwidth ÷ weight size, one user) is the arithmetic that follows from that: each new token reads every weight once.
  • For scale, Intel's own measurement: two Xeon 6980P with 24 × 96 GB MRDIMM-8800 served Llama 3.1 8B at 1,139.51 tokens per second in MLPerf Inference v6.1, Server scenario, CPU only (Intel newsroom, September 2026). That is total throughput across all users, not one user's speed. For a measured figure on a specific SKU and model, use Intel's On-prem AI Performance Advisor.
  • Two ways to use the nodes. Intel's vLLM on Xeon guide sets --tensor-parallel-size to the NUMA node count, so one instance keeps a shard of the model on each node's local memory; that is the "one instance across all nodes" option, and it adds up every node's bandwidth for each user, minus the cost of communication between nodes. Running one copy per node instead (data parallel) keeps every node independent and loses nothing to communication, but each user only gets one node's bandwidth. Tensor parallel needs the attention heads to split evenly across the nodes. The guide also suggests --max-num-seqs 128 online and 256 offline.
  • Mixture-of-experts reads: the page splits the weights into a shared part and an expert part from the total and active parameter counts, and counts the experts a batch of b users touches as 1 − (1 − k/E)b of them (Qwen3-30B-A3B: 8 of 128 experts per token). It assumes experts are picked independently, which is a planning estimate.
  • Model numbers and the KV cache formula are the same as on page 1. All figures are planning estimates: measure with real prompts before setting limits.
